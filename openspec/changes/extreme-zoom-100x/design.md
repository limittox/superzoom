# Design

## Context

See proposal.md for motivation. Current behaviour (main specs and code as of 2026-10-07):

- `computeMaxZoom()` in `src/camera/crop.ts` gives `C × sqrt(visiblePixels / 1 MP)`, and `computeCrop()` clamps the digital factor to keep at least 1 MP. On the test Samsung (C = 5, 12.5 MP photos, a visible region of about 1882 × 4080 at a 2.168 screen ratio), that's about 13.9x.
- `chooseUpscaleFactor()` (`src/shared/upscale.ts`) clamps to `LIMITS.minUpscale`–`maxUpscale` (2–4) and to at most 16 MP of output. The server rejects inputs with a short side under 64 px or over 4 MP.
- fal limits, from fal's model docs: SeedVR2 `upscale_factor` goes up to 10; Topaz and Clarity go up to 4.
- VisionCamera 5 accepts a `previewStabilizationMode` constraint (`'auto'`, `'preview-optimized'`, …). Constraints are best-effort; unsupported ones are ignored.

## Goals / Non-Goals

**Goals:**
- Reach 100x where the sensor still gives a crop of at least 64 px on the short side.
- Make clear in the UI when a result is mostly generated.
- Keep the request/response contract and the 4 MP input and 16 MP output caps.

**Non-Goals:**
- Multi-frame burst merging (the real quality fix; a later change).
- Software stabilization or frame alignment.
- Per-mode pricing or rate limits.

## Decisions

### 1. Two limits from one function
`computeZoomLimits(opticalCapDisplay, photoW, photoH, screenLongOverShort)` returns:
- `nativeLimit = C × sqrt(visiblePixels / 1 MP)` (today's `computeMaxZoom`), and
- `maxZoom = min(100, C × visibleShortSide / 64)`.

`computeCrop()` clamps the digital factor so the crop's short side stays at least 64 px, instead of at least 1 MP, and `isFramingClamped()` uses the same bound. `MIN_CROP_SHORT_SIDE` comes from `LIMITS.minSidePx`, so the app and server can't drift apart.
- *Why short side, not pixel count:* the server's real constraint is a 64 px short side, and short side also limits what the upscaler can do.
- *Alternative:* a lower pixel floor, such as 0.01 MP. It's equivalent on 4:3 sensors but doesn't line up with the server check.

### 2. Zoom tiers as a pure function
`zoomTier(zoom, opticalCap, nativeLimit)` returns `'optical' | 'ai' | 'reconstructed'`, with the same 0.05 tolerance the indicator uses today. `ZoomControls` takes `nativeLimit`:
- **Badge:** "AI ZOOM" for the AI tier, "AI-RECONSTRUCTED" in a stronger colour for the reconstructed tier.
- **Hint:** in the reconstructed tier, one line: "Most detail will be generated by AI. Brace your phone."

**Presets:** the beyond-optical candidates `[10, 20, 30, 50, 100]` within `maxZoom` and above 1.5 × C, with at most three shown, spread out (first, middle, last), so the test phone shows 10x, 30x and 100x.

### 3. Capture marks AI-reconstructed results
`useZoomCamera().capture()` returns `aiReconstructed = zoom > nativeLimit + tolerance`. `startSession()` stores it. The result screen labels such results "AI-reconstructed (<mode>)" with the generated-detail note, which replaces the Creative caveat for those captures.

### 4. Upscale factor up to 10x, two passes for 4x models
- `LIMITS.maxUpscale` becomes 10; `chooseUpscaleFactor()` is unchanged otherwise (largest factor ≤ 10 keeping output ≤ 16 MP). A 94 × 204 crop gets 10x (about 1.9 MP), and a 1000 × 1000 crop still gets 4x.
- `MODEL_TABLE` entries gain `maxFactorPerPass` (SeedVR2 10, Topaz 4, Clarity 4). When the factor exceeds it, the fal upscaler runs pass 1 at `min(maxFactorPerPass, f)` and pass 2 at the remaining `f / f1` (always ≥ 1 and ≤ 4 when f ≤ 10). Pass 2 takes pass 1's output URL directly, with no re-upload.
- Both passes share the request's abort signal, so the existing **120 s total timeout** still applies. Output dimensions are the planned size unless fal reports them.
- *Alternative:* equal passes (√f each). That spreads generation more evenly but costs the same; the first-pass-max approach keeps pass 2 small for Clarity's per-MP billing. Either satisfies the spec.

### 5. Preview stabilization, conditional on framing
The `Camera` gets `constraints={[{ previewStabilizationMode: 'auto' }]}`. Stabilization often crops the preview by a few percent, which would make the preview show less than the photo, so the capture crop would be wider than what the user framed (spec: Capture crops to the framed region). A device task checks framing at about 50x with stabilization on. If the framing is off by more than about 3%, the constraint is removed and the brace hint stays. Removing it is one line.

### 6. Testing
Jest:
- `computeZoomLimits` and the 64 px clamp: Samsung, main-lens-only and 48 MP cases.
- `zoomTier`, and preset selection.
- `chooseUpscaleFactor` at 10x.
- Two-pass fal calls with a mocked client: endpoints, factors, pass-2 URL, shared timeout.
- The session flag, and the result label logic as a pure function.

Device:
- 100x reachable, tiers and hint, framing at 50x.
- Enhance, Pro and Creative at 100x, within the timeout.

## Risks / Trade-offs

- [Results past about 14x are mostly invented] → the AI-reconstructed tier, warning and label; the result screen's comparison shows how little was there.
- [Two passes double Topaz cost (about $0.16) and add latency] → only when f > 4, which needs inputs under 1 MP. Bounded by the existing 120 s timeout and rate limit.
- [Preview stabilization changes framing] → decision 5's device check, with removal as the fallback.
- [A 20x digital preview is very soft and shaky] → it's a framing aid only. The hint, stabilization where it's safe, and lens detents still apply below 5x.
- [Generative second passes may amplify artifacts] → acceptable for an explicitly AI-reconstructed tier; Enhance (single-pass SeedVR2) remains the default.

## Migration Plan

The zoom and enhancement changes are app (JavaScript) and backend only, so they work on an existing dev build. The `getExtensionInfo` Camera2 query added during device testing is native code in `modules/lens-info`: builds made before it lack the method, and the wrapper returns `null` there, so it needs a rebuilt app. Deploy order: backend (dev server now, EAS Hosting later), then the app. Older app versions keep working, since they only send crops of at least 1 MP.

## Open Questions

- The exact tolerance for "framing off" in decision 5 (about 3%) can be tuned during the device check without changing the plan.
